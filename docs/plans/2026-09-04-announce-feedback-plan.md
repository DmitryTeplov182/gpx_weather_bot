## 1. При редактировании анонса теряется один из дашбордов

**Диагноз.** Это не гонка и не баг с файлами, а осознанная инвалидация без перегенерации.
В `preview_handler` ([announce_bot.py:2048](../../announce_bot.py#L2048)) при нажатии любой кнопки «Изм. …»:

- дата/время: `invalidate_generated_images(context)` удаляет и постер, и погодный дашборд;
- название/старт/темп/комментарий: `invalidate_generated_images(context, dashboard=False)` удаляет только постер;
- ссылка Komoot: удаляет оба.

После возврата в `preview_step` ничего не пересоздаётся, и пользователь видит одну картинку
вместо двух (или ни одной). Кнопка «Сгенерировать постер» появляется, но выглядит как потеря.
Своя картинка (`ask_image` с фото) тоже удаляет оба сгенерированных файла.

**Воспроизведение.** `/start` → трек → «Оба» → превью с двумя картинками → «💬 Изм. коммен.» →
ввести текст → превью показывает только погодный дашборд.

**Решение (PR 1, механизм; PR 4, упрощение).**

1. Вместо удаления файлов помечать их устаревшими: `context.user_data['stale_images'] = {'poster', 'dashboard'}`.
   Хранить, какие картинки пользователь выбирал: `context.user_data['wanted_images']`.
2. В начале `preview_step` вызывать `regenerate_stale_images(update, context)`: для каждого
   устаревшего и желаемого изображения вызывать существующие `generate_poster_for_announce` /
   `generate_dashboard_for_announce`. Постер строится за секунды. Погода при смене только времени
   попадает в кэш `requests_cache` (ключ включает дату, а не час), так что перерисовка быстрая.
3. Удалять файлы физически только по кнопкам «🗑️ Удалить …» и при замене своей картинкой.
4. После PR 3 останется одна картинка, и механизм сводится к одному флагу `dashboard_stale`.

**Файлы.** `announce_bot.py`: `invalidate_generated_images`, `preview_step`, `preview_handler`, `ask_image`.

**Проверка.** Сценарий выше: после правки комментария в превью снова две картинки, при правке
времени обе перестроены с новым временем. Правка ссылки Komoot тоже перестраивает.

## 4. Неверный максимальный градиент и единый дашборд

### 4a. Градиент (PR 1)

**Диагноз.** Высота сглаживается трижды до вычисления max grade в `ride_poster.py`:

1. `parse_gpx` → `resample_route(step_m=100)` + `moving_average(ele, 7)` (окно 700 м);
2. `detect_major_climbs` → ещё `moving_average(route.ele, 9)` (окно 900 м);
3. `grade_percent(window_m=300)` + `moving_average(grades, 5)`.

Итоговое окно больше километра, короткие крутые участки съедаются.

**Измерено** на туре 2551875808 (Rakovac - Venac, подъём 10.1–17.6 км, +357 м) скриптом
[tools/grade_experiment.py](../../tools/grade_experiment.py) (принимает GPX или JSON координат Komoot):

| Вариант | max grade |
|---------|-----------|
| текущий конвейер | 9.2% |
| 100 м шаг, MA3, окно 200 м | 10.7% |
| 50 м шаг, MA3, окно 100 м | 11.9% |
| 25 м шаг, MA5, окно 100 м, MA3 | 12.0% |
| 50 м шаг, без MA, окно 100 м | 12.3% |

Komoot показывает 13%. Остаток разницы — другая модель рельефа у Komoot, а не наше сглаживание.

**Решение.**

- В `RouteData` хранить сырые высоты (`raw_ele`, `raw_dist_km`), а не только пересэмпленные.
- Оставить сглаженный профиль для поиска начала/конца подъёмов (там он полезен).
- `max_grade` считать по отдельному «тонкому» градиенту: пересэмплинг 50 м, `moving_average(3)`,
  окно 100 м, без пост-сглаживания, максимум внутри границ подъёма. Ожидаемо 12% для Rakovac.
- В легенде профиля и в списке подъёмов подписать «max over 100 m», чтобы цифра была честной.

**Проверка.** `python tools/grade_experiment.py` на координатах 2551875808 и на
`routes/Bukovac from flags-2070100198.gpx`: Rakovac ≥ 12%, Bukovac ≈ 8.4% (сейчас 6.9%).

## 5. Темп опциональный, скорость диапазоном через тире

**Диагноз.** `ask_pace` принимает только пять строк из `PACE_OPTIONS` (луны). Скорость для прогноза
захардкожена: `generate_weather_dashboard(..., speed_kmh=27)`.

**Решение (PR 2).**

- Клавиатура темпа: пять лун + «⏭️ Без темпа». Свободный текст парсить регуляркой
  `^\s*(\d{1,2})\s*(?:[-–—]\s*(\d{1,2}))?\s*(км/ч|km/h)?\s*$` → `speed_range = (lo, hi)`;
  одно число → `(v, v)`. Валидация 10–60 км/ч.
- В `user_data`: `pace` (луны или `None`), `speed_range` (кортеж или `None`).
- Строка анонса: `Ожидаемый темп: 🌝🌝🌚`, или `Средняя скорость: 25–28 км/ч`, или строка
  опускается. Не забыть оба места, где строится анонс (`preview_step` и ветка «Отправить» в
  `preview_handler` дублируют код; вынести в `build_announce_text(user_data)`).
- Скорость для прогноза: середина диапазона; иначе по лунам через
  `PACE_TO_SPEED = {1.0: 22, 1.5: 24, 2.0: 27, 2.5: 30, 3.0: 33}`; иначе 27.
- На картинке чип PACE: точки при лунах, текст `25–28 km/h` при диапазоне, чип скрыт, если ничего.
- `quick_mode` после даты тоже спрашивает темп, там та же клавиатура.

**Файлы.** `announce_bot.py`: `ask_pace`, `preview_step`, `preview_handler`, `generate_ride_poster`,
`generate_weather_dashboard`, `handle_time_selection`, `ask_date_time`; `ride_poster.py`: `add_pace_chip`.

## 6. Направление ветра: график tailwind/headwind

**Диагноз.** Сейчас ветер показан крупными стрелками на карте (`mutation_scale` 12–15, длина 22 pt)
и графиком скорость/порывы. Стрелки не отвечают на вопрос «в спину или в лицо».

**Решение (PR 3).**

- Для каждого 100-метрового сегмента трека взять курс θ (bearing) и ближайшую по дистанции точку
  прогноза (ветер `wind_direction_10m` — направление, откуда дует).
  Продольная составляющая `along = -speed · cos(φ_from − θ)`, положительная = попутный.
  Боковая `cross = |speed · sin(φ_from − θ)|`.
- Свести к временной оси через время прохождения сегмента (та же скорость, что в прогнозе),
  усреднить по 10-минутным корзинам.
- График: столбики/область над нулём зелёным (SECONDARY, tailwind), под нулём красным (ACCENT,
  headwind), тонкая линия crosswind серым, подписи `+km/h tail / −km/h head`. Ось X — время.
- На карте стрелки оставить, но вдвое меньше (`mutation_scale` 7, длина 10 pt) и через одну точку.
  Замечание сформулировано как «либо/либо», рекомендую график как основной, стрелки как
  вспомогательные, потому что карта на едином дашборде всё равно есть.

**Проверка.** Синтетический тест: прямой трек на север и ветер с юга даёт +speed, с севера
−speed, с востока 0 по продольной и speed по боковой.

## 7. Температура и вероятность дождя одним полем

**Диагноз.** Плитки Temperature и Feels Like уже дают диапазон, но дождь только на графике
осадков (мм + вероятность + облачность), который занимает половину среднего ряда.

**Решение (PR 3).**

- Плитки: `Temp 18–24 °C` (подстрока `feels 16–23`), `Rain 10–40 %` (подстрока `max 0.6 mm/h`
  только если осадки > 0). Минимум/максимум по точкам прогноза за время заезда.
- График осадков убрать, место уходит карте и графику ветра.

## 8. Описание покрупнее

**Диагноз.** Комментарий анонса попадает в `notes` и рисуется как подзаголовок панели профиля
(`rounded_panel(..., subtitle=notes)`) шрифтом `fs(10)` цветом SUBTLE, максимум 3 строки.

**Решение (PR 3).** Отдельный блок под шапкой: `fs(13.5)`, цвет INK, до 4 строк с переносом через
`fig_fit_text(max_lines=4)`, минимум `fs(11)` при длинном тексте.

## 10. На профиле высоты нет обозначений по оси Y

**Диагноз.** `draw_profile` явно делает `ax.set_yticks([])` ([ride_poster.py:747](../../ride_poster.py#L747)).

**Решение (PR 1).** Шаг тиков по диапазону (`50/100/200 м`), 3–5 тиков, подписи `fs(9.5)` SUBTLE,
формат `{v:.0f} m`, лёгкая горизонтальная сетка BORDER. Учесть headroom для бейджей подъёмов:
верхняя граница `y_top` не должна получать тик, чтобы подписи не залезали на бейджи.

## 11. На дашборде заезда у карты нет OSM-подложки

**Диагноз.** `draw_map` в `ride_poster.py` рисует трек в нормализованных координатах 0..1 без
проекции, поэтому подложку туда не положить. В `weather_dashboard.py` карта уже в Web Mercator с
`contextily` и правильным User-Agent.

**Решение (PR 3, при желании раньше).** Вынести из `weather_dashboard.py` в общий модуль
`map_panel`, `route_map_bounds`, `expand_bounds_to_axes_aspect`, `latlon_to_web_mercator`,
`osm_tile_headers` и рисование трека/маркеров. `draw_map` постера переписать на них: подложка,
трек, S/F, номера подъёмов по индексу дистанции. Включить `ctx.set_cache_dir('cache/tiles')`,
чтобы повторные рендеры того же маршрута не ходили за тайлами. При ошибке сети — как сейчас,
трек без подложки и предупреждение в лог.

## Риски и заметки

- Единый дашборд зависит от сети (Open-Meteo, тайлы OSM). Обязателен graceful fallback, иначе
  анонс без картинки при любом сбое.
- `generate_weather_dashboard` вызывает `python3` буквально, на Windows-разработке это не
  работает; заменить на `sys.executable`, как уже сделано для постера.
- `preview_step` и «Отправить» дублируют сборку текста анонса; при добавлении строки скорости легко
  поправить одно место и забыть второе. Вынести в одну функцию в PR 2.
- Переименование точек ломает старые `ready_routes.json` у тех, кто держит локальные копии;
  отметить в README.
