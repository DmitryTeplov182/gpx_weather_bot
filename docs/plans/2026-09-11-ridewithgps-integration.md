# RideWithGPS + ревизия кэша GPX: план работ

Дата: 2026-09-11. Ветка: `claude/ridewithgps-integration-2b0263`.

**Статус:** реализовано в этой же ветке 2026-09-11 одним PR (разделы 5–7 целиком).
Все факты ниже проверены живыми запросами, разведочный скрипт — в
[`tools/rwgps_probe.py`](../../tools/rwgps_probe.py).

Решения по открытым вопросам раздела 9: `trips` поддержаны наравне с `routes`;
об обновлении маршрута бот сообщает всегда, с цифрами «было/стало»; фоллбэк по ключу
написан по спецификации, но вживую не проверялся — аккаунта RideWithGPS нет.

**Решение по архитектуре:** основной путь — бесключевой эндпоинт
`https://ridewithgps.com/{routes|trips}/{id}.json`, фоллбэк — официальный API v1 с парой
`api_key` + `auth_token`. Оба пути прячутся за одним провайдером, боты о них не знают.

**Ключи не протухают** — см. раздел 3.

Вторая половина плана — про кэш GPX. Там нашлось шесть дефектов, и один из них
(раздел 5.2) прямо объясняет жалобу «подтягивается старый файл и часть старой инфы».
Чинить кэш надо **до** добавления второго провайдера, иначе те же грабли размножатся.

## 1. Короткая сводка проверенного

| Запрос | Ответ |
|--------|-------|
| `GET /routes/{id}.json` без авторизации | **200**, полный трек с высотами + метаданные |
| то же со слагом `/routes/12345-walnut-via-verde.json` | **200**, тот же ответ |
| `GET /trips/{id}.json` | **200**, записанный заезд (время, пульс, каденс, мощность) |
| `GET /routes/{id}.gpx` / `.tcx` / `.kml` | **401**, отдаётся HTML логина |
| `GET /api/v1/routes/{id}.json` без ключа | **401** `{"errors":["Failed to authenticate the request"]}` |
| приватный маршрут | **403** `{"error_code":"not_public"}` |
| несуществующий | **404** `{"success":0,"message":"Record not found"}` |
| **`If-None-Match` с сохранённым ETag** | **304**, 0 байт, 0.6 с |

Скорость: 1.24–1.34 с на маршрут 62 км (377 КБ JSON). Ревалидация через 304 — 0.6 с и ноль трафика.
Для сравнения: `komootgpx` запускается подпроцессом с таймаутом 60 с.

Сборка GPX из `track_points` проверена: XML парсится `ElementTree`, `metadata/name` и `trk/name`
на месте (то есть [`extract_route_name_from_gpx`](../../announce_bot.py#L259) найдёт название),
у всех 5884 точек есть `<ele>`, длина по haversine сходится с метаданными до 0.1 %.
`detect_timezone_from_gpx` и `ride_dashboard.py` едят такой файл без правок.

`elevation_gain` у RWGPS сглаженный, как `elevation_up` у Komoot: на проверенном маршруте
RWGPS даёт 1309 м против 1773 м сырого пересчёта по точкам. Логика
[`fetch_komoot_tour_meta`](../../announce_bot.py#L70) («метаданные точнее GPX») переносится один в один.

## 2. Формат ответа и распознавание ссылок

Поля объекта маршрута (`/routes/{id}.json`):

```
id, name, description, distance (м), elevation_gain (м), elevation_loss (м),
created_at, updated_at (unix!), first_lat, first_lng, bounding_box,
locality, administrative_area, country_code, visibility (0 = public), privacy_code,
track_type (loop / out_and_back), terrain, difficulty, surface, unpaved_pct,
pavement_type, activity_types, track_points[], course_points[], points_of_interest[]
```

`updated_at` — семантический ключ свежести, пригодится в разделе 6.

Точки (по [справочнику API](https://ridewithgps.com/api/v1/doc/reference/track_points)):

| Поле | Значение | Route | Trip |
|------|----------|-------|------|
| `x` / `y` | долгота / широта | да | да |
| `e` | высота, м | да | да |
| `d` | расстояние от старта, м | да | да |
| `S` / `R` | тип покрытия / highway-тег OSM | да | — |
| `t` | unix-время | — | да |
| `s`, `h`, `c`, `p`, `T` | скорость, пульс, каденс, мощность, температура | — | да |

Ссылки, которые надо ловить:

- `https://ridewithgps.com/routes/12345`
- `https://www.ridewithgps.com/routes/12345-slug-маршрута` (слаг работает и в `.json`)
- `https://ridewithgps.com/trips/12345`
- `https://ridewithgps.com/routes/12345?privacy_code=abc123`
- `https://ridewithgps.com/embeds?type=route&id=12345`
- без схемы: `ridewithgps.com/routes/12345`

Короткого домена (вроде `rwgps.co`) у сервиса нет — DNS не резолвится.

```python
RWGPS_LINK_PATTERN = re.compile(
    r'(?:https?://)?(?:www\.)?ridewithgps\.com/(routes|trips)/(\d+)', re.IGNORECASE)
RWGPS_EMBED_PATTERN = re.compile(
    r'(?:https?://)?(?:www\.)?ridewithgps\.com/embeds\?[^ ]*\btype=(route|trip)\b[^ ]*\bid=(\d+)',
    re.IGNORECASE)
PRIVACY_CODE_PATTERN = re.compile(r'[?&]privacy_code=([A-Za-z0-9_-]+)')
```

## 3. Ключи: протухают или нет

**Не протухают.** Проверено по официальной OpenAPI-спеке
([`ridewithgps.com/api/v1/openapi.yaml`](https://ridewithgps.com/api/v1/openapi.yaml), 122 КБ):

- схема `AuthToken` содержит ровно `auth_token`, `api_key`, `created_at`, `updated_at`, `user` —
  **поля срока жизни нет**;
- во всей спеке **ноль** упоминаний `expir`, `refresh_token`, `ttl`;
- в OAuth-ответе из [документации](https://ridewithgps.com/api/v1/doc/getting_started/authentication)
  тоже нет ни `expires_in`, ни `refresh_token`, зато есть явный `POST /oauth/revoke.json`.

То есть токен живёт, пока его не отозвали руками. Пара кладётся в секреты один раз:

```
RWGPS_API_KEY=...
RWGPS_AUTH_TOKEN=...
```

Передаются заголовками `x-rwgps-api-key` и `x-rwgps-auth-token` (либо Basic
`base64(api_key:auth_token)`). Получаются так: завести боту бесплатный аккаунт →
[страница API-клиентов](https://ridewithgps.com/api/api_clients) → выдаётся `api_key` →
один `POST /api/v1/auth_tokens.json` с почтой и паролем возвращает `auth_token`.

Оговорка: «срок не документирован» ≠ «гарантированно вечно». Поэтому в коде — обработка 401 на
фоллбэк-пути: залогировать как ошибку конфигурации и продолжить работать основным путём, а не падать.
Автопродление (хранить почту/пароль и перевыпускать токен) — не делаем: держать пароль в `.env`
ради ветки, которая срабатывает раз в год, невыгодно.

**Что ещё даёт ключ** (проверено по спеке):

- `GET /api/v1/routes/{id}.json` → ответ **обёрнут**: `{"route": {...}}`, в отличие от легаси,
  где объект лежит в корне. Это надо учесть в парсере;
- `GET /api/v1/routes/{id}.{gpx|tcx|fit|kml}` → «GPX 1.1 track at full resolution, without waypoints» —
  готовый файл, собирать из точек не нужно;
- «Visibility rules are the same as for the JSON record: a non public route needs a `privacy_code`
  unless it belongs to the authenticated user» — то есть **чужие публичные маршруты доступны**
  (это был открытый вопрос прошлой версии плана, теперь закрыт);
- `privacy_code` — официальный query-параметр обоих эндпоинтов.

## 4. Провайдер RWGPS: основной путь и фоллбэк

```
fetch_rwgps(ref):
    1) GET https://ridewithgps.com/{kind}/{id}.json[?privacy_code=...]
       заголовки: User-Agent с контактом, If-None-Match если есть сохранённый ETag
       304 -> кэш актуален, выходим
       200 -> собрать GPX из track_points, вернуть метаданные
       403 -> «маршрут приватный» (в фоллбэк не идём: там будет то же самое)
       404 -> «маршрут не найден» (в фоллбэк не идём)
       5xx / таймаут / не-JSON -> ФОЛЛБЭК
    2) фоллбэк, только если заданы RWGPS_API_KEY и RWGPS_AUTH_TOKEN:
       GET https://ridewithgps.com/api/v1/routes/{id}.gpx[?privacy_code=...]
       заголовки: x-rwgps-api-key, x-rwgps-auth-token
       200 -> писать файл как есть (это уже GPX 1.1)
       401 -> logger.error про ключи, пробросить исходную ошибку основного пути
    3) ключей нет или фоллбэк не сработал -> понятная ошибка пользователю
```

Почему именно так, а не наоборот:

- бесключевой путь работает у любого, кто клонировал репозиторий, — не требует заводить аккаунт;
- он же даёт `updated_at` и ETag, на которых строится ревалидация кэша (раздел 6);
- фоллбэк закрывает единственный реальный риск: `robots.txt` RideWithGPS запрещает роботам
  `/routes/*.json`, `/trips/*.json` и `/*.gpx*`
  ([robots.txt](https://ridewithgps.com/robots.txt)). Формально это директива для краулеров, а бот
  ходит по присланной человеком ссылке и один раз на маршрут, но если сервис начнёт резать —
  переключение стоит одной переменной окружения.

Гигиена основного пути: осмысленный `User-Agent` с контактом, обязательный кэш по id,
никакого перебора id, таймаут 30 с.

Метаданные фоллбэка: `.gpx` их не отдаёт, поэтому при фоллбэке длину и набор считаем по GPX
(как сейчас делается для Komoot при недоступности API) либо дополнительно дёргаем
`/api/v1/routes/{id}.json` и берём `route.distance` / `route.elevation_gain`. Предлагаю второе —
запрос дешёвый, а цифры сглаженные и потому точнее.

## 5. Ревью кэширования: что сломано сейчас

Кэш — это `cache/*.gpx`, имена вида `{title}-{tour_id}.gpx` (так пишет `komootgpx`, паттерн
по умолчанию `{title}-{id}.gpx`). Поиск везде одинаковый: `glob.glob(f"{CACHE_DIR}/*-{tour_id}.gpx")`.

### 5.1. Свежесть не проверяется вообще

Три места берут файл из кэша и не спрашивают провайдера, актуален ли он:

- [announce_bot.py:594](../../announce_bot.py#L594) — команда `/weather`: `gpx_files[0] if gpx_files else None`;
- [announce_bot.py:2170](../../announce_bot.py#L2170) — `preload_ready_routes`: `if gpx_files: continue`;
- [announce_bot.py:2220](../../announce_bot.py#L2220) — `preload_ready_routes_sync`: то же самое.

Единственная «инвалидация» — уборка старше 180 дней. Отредактировали маршрут в Komoot —
бот полгода рисует старый трек. И бьёт это по самому частому сценарию: `preload_*` кэширует
именно готовые маршруты из `ready_routes.json`, те, что показаны кнопками.

### 5.2. Переименование маршрута плодит двойники, и берётся случайный

`komootgpx` вызывается с `-d <tour_id>`, а флаги `-s/--skip-existing` и `-S/--skip-unchanged`
[по документации самого komootgpx игнорируются вместе с `-d`](https://github.com/timschneeb/KomootGPX) —
то есть файл пишется всегда, с именем из **текущего** названия тура.

Переименовали тур в Komoot → в `cache/` лежат два файла с одним `tour_id`:
`Старое имя-2526993761.gpx` и `Новое имя-2526993761.gpx`. `glob` возвращает их в порядке
`os.scandir`, то есть без гарантий, а код берёт `[0]`.

**Это и есть «подтягивается старый файл и часть старой инфы».** Причём в самом неприятном виде:
в [`process_gpx`](../../announce_bot.py#L1102) длина и набор берутся из **свежего** ответа Komoot API
([announce_bot.py:1177](../../announce_bot.py#L1177)), а трек — из `glob(...)[0]`, который может
оказаться **старым**. В анонс уходит новая длина, на дашборд — старый трек, и расходятся они молча.

Затронуты все четыре места с `glob(...)[0]`: [announce_bot.py:594](../../announce_bot.py#L594),
[:625](../../announce_bot.py#L625), [:1143](../../announce_bot.py#L1143),
[weather_bot.py:593](../../weather_bot.py#L593).

### 5.3. TTL считает не возраст кэша, а дату правки маршрута

`komootgpx` после записи делает `os.utime(path, (changed_at, changed_at))` — ставит файлу mtime,
равный дате последнего изменения тура. А
[`cleanup_old_gpx_files`](../../announce_bot.py#L2090) сравнивает mtime с «сейчас» и удаляет всё
старше 180 дней.

Получается ровно наоборот от нужного: маршрут, нарисованный два года назад и с тех пор не
менявшийся (то есть заведомо актуальный), выкидывается при каждой уборке и качается заново, —
а маршрут, отредактированный вчера (то есть тот, который правят чаще всего), остаётся в кэше.
Как политика вытеснения mtime здесь не значит ничего.

### 5.4. Ключ кэша не различает провайдеров

`*-{tour_id}.gpx` — это только id, без источника. Komoot tour `12345` и RideWithGPS route `12345` —
разные маршруты, но один и тот же glob. Сегодня это не баг, с появлением RWGPS станет им.

### 5.5. Избранное в weather_bot — снимок навсегда

[`favorite_routes`](../../favorites_db.py#L27) хранит `gpx_blob` и рядом `komoot_url`.
Ссылка есть, пути обновления нет: сохранил избранное — получил GPX на день сохранения.
Для «избранного» это отчасти осознанно (снимок), но пользователь об этом не знает и не может
обновить, кроме как удалив и создав заново.

### 5.6. Ошибка сети = потеря маршрута

Сейчас при падении скачивания диалог просто откатывается на «пришли другую ссылку»
([announce_bot.py:1128](../../announce_bot.py#L1128)), хотя рядом в кэше может лежать
вчерашняя копия того же маршрута. После ввода ревалидации это станет критично: недоступность
провайдера не должна ронять сценарий, у которого есть валидный кэш.

## 6. Как чинить кэш

### Единица кэша = два файла

```
cache/{provider}-{id}.gpx          # komoot-2526993761.gpx, rwgps-45000000.gpx
cache/{provider}-{id}.meta.json    # сайдкар
```

Детерминированное имя без названия маршрута убирает 5.2 и 5.4 сразу: один маршрут — один файл,
переименование его перезаписывает, а не клонирует. Сайдкар:

```json
{
  "provider": "komoot",
  "id": "2526993761",
  "url": "https://www.komoot.com/tour/2526993761",
  "etag": "W/\"8bb21e...\"",
  "remote_updated_at": "2025-08-25T15:54:17.390Z",
  "name": "Rumenka - Futog - Jama",
  "distance_m": 51007.1,
  "elevation_up": 57.9,
  "elevation_down": 58.1,
  "fetched_at": "2026-09-11T08:46:00Z",
  "last_used_at": "2026-09-11T08:46:00Z",
  "gpx_sha256": "..."
}
```

Пишется атомарно: временный файл + `os.replace`, сначала `.gpx`, потом сайдкар. Если процесс
убили посередине — сайдкара нет, значит кэша нет, значит перекачаем. Сайдкар без `.gpx` — то же самое.

### Проверка свежести

Обе платформы отдают ETag и понимают условный запрос — проверено:

| | ревалидация | цена |
|---|---|---|
| RideWithGPS | `GET /routes/{id}.json` + `If-None-Match` → **304** | 0.6 с, 0 байт |
| Komoot | `GET api.komoot.de/v007/tours/{id}` + `If-None-Match` → **304** | 0.2 с, 0 байт |

Алгоритм `ensure_gpx(ref)`:

1. нет `.gpx` или нет сайдкара → качаем, `changed = True`;
2. есть оба → условный запрос с сохранённым ETag:
   - **304** → кэш актуален, `changed = False`, обновляем `last_used_at`; для Komoot это стоит
     одного запроса, который [`fetch_komoot_tour_meta`](../../announce_bot.py#L70) **и так уже делает**,
     так что накладных расходов нет вовсе;
   - **200** → сверяем семантический ключ (`updated_at` у RWGPS, `changed_at` у Komoot)
     с сохранённым. Совпал → ETag просто протух по техническим причинам, GPX не трогаем,
     обновляем сайдкар. Не совпал → перекачиваем, `changed = True`;
3. сеть легла / 5xx / таймаут → **используем кэш** и возвращаем `stale = True`;
4. 403/404 → внятная ошибка, кэш (если есть) не трогаем.

Возвращаем `RouteData(gpx_path, meta, changed, stale)`.

ETag у RWGPS слабый (`W/"..."`), но проверено: стабилен между запросами без cookies (три подряд —
один и тот же). Худший случай ложного срабатывания — лишняя перекачка, не порча данных.

### Инвалидация вниз по цепочке

`changed = True` означает: перечитать `length_km`, `uphill`, `extracted_name` из свежих
метаданных **и** пометить сгенерированные картинки устаревшими — механизм `stale_images` /
`refresh_dashboard_if_stale` для этого уже есть
([план от 2026-09-04](2026-09-04-announce-feedback-plan.md)). Плюс сказать пользователю прямо:

> 🔄 Маршрут обновился в Komoot: было 51 км / 58 м, стало 54 км / 120 м. Пересобираю дашборд.

`stale = True` — тоже сказать, но мягко:

> ⚠️ Не смог проверить актуальность маршрута (Komoot не ответил). Показываю версию от 10.09.

### TTL и уборка

`cleanup_old_gpx_files` перестаёт смотреть на mtime (5.3) и работает по `last_used_at` из сайдкара —
то есть становится честным LRU: удаляем то, чем не пользовались N дней, вместе с сайдкаром.
Раз есть ревалидация, TTL нужен только чтобы не пух диск, и 180 дней можно оставить.

### Миграция

Старые файлы `{title}-{id}.gpx` сайдкара не имеют → при первом обращении трактуются как
«кэша нет» и перекачиваются в новое имя. Одноразовая уборка при старте сносит всё, что не
подходит под `{provider}-{id}.gpx`. Терять нечего: это кэш.

### Избранное

В `favorite_routes` добавить `provider`, `source_id`, `remote_updated_at`, `etag`
(`komoot_url` оставить, переименование колонки не стоит миграции). При использовании избранного,
у которого есть ссылка, — тот же `ensure_gpx`; если `changed`, спросить:
«Маршрут обновился с момента сохранения. Обновить избранное?» — и не перезаписывать молча.

## 7. Что сделано

Планировалось четырьмя PR, сделано одним — по просьбе. Ниже исходная разбивка,
она же порядок работ внутри коммита.

### PR 1. Кэш GPX: сайдкары, ревалидация, честный TTL

Только Komoot, без RideWithGPS. Чинит 5.1–5.3, 5.6 и готовит почву под второго провайдера.

Новый модуль `route_cache.py`:

```python
cache_paths(provider, id) -> (gpx_path, meta_path)
read_meta(provider, id) -> dict | None
write_entry(provider, id, gpx_bytes, meta)        # атомарно
touch_used(provider, id)
purge_unused(days)                                 # LRU по last_used_at
```

## 8. Что можно взять сверх нынешнего функционала

RideWithGPS в том же ответе отдаёт то, чего у Komoot нет:

- `unpaved_pct` и `surface` — доля грунта, просится в анонс;
- `S` на каждой точке — раскрасить трек на карте по типу покрытия;
- `course_points` — готовый кью-шит с поворотами;
- `elevation_loss` — сброс, сейчас нигде не показывается;
- `track_type` (`loop` / `out_and_back`), `difficulty`;
- `/trips/{id}` — записанные заезды с временем, пульсом, мощностью: сценарий «дашборд по факту
  заезда», которого сейчас нет вообще.

Поэтому в `RouteData` и заложено поле `extra`, а не жёсткая пара «длина + набор».

Побочная находка про Komoot: у тура есть `_links.coordinates` →
`https://api.komoot.de/v007/tours/{id}/coordinates`, то есть точки доступны тем же способом, что и
у RideWithGPS, и от подпроцесса `komootgpx` в принципе можно избавиться. В этот план не входит,
но после PR 2 это станет заменой одного метода одного провайдера.

## 9. Что осталось непроверенным

1. **Фоллбэк по ключу** написан по OpenAPI-спецификации, но вживую не гонялся: аккаунта
   RideWithGPS нет. Проверить, когда заведутся `RWGPS_API_KEY` и `RWGPS_AUTH_TOKEN`.
2. **`privacy_code`** на живой приватной ссылке не проверялся — нужен реальный пример.
   Параметр официальный, разбор ссылки и проброс в запрос тестом покрыты.
3. **Обновление избранного** в `weather_bot` сделано без диалога подтверждения: при
   изменении маршрута снимок переписывается сразу и бот об этом пишет. Если нужен именно
   вопрос «обновить?», это ещё одно состояние в `ConversationHandler`.
4. **Шум от сообщений об обновлении**: сейчас бот сообщает о любом изменении маршрута.
   Если правка одной точки будет раздражать — добавить порог (скажем, 1 % по длине).
